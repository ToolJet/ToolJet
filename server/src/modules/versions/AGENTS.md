# versions module

Owns the AppVersion lifecycle: named development snapshots of an App. Create/clone a version (deep definition copy), edit it as a DRAFT, save (PUBLISHED), promote it across App Environments (EE), and delete it. **Release itself lives in the apps module** (`apps/service.ts` `release()` sets `apps.current_version_id`); this module supplies the eligibility checks. Also owns version-scoped page/component/event endpoints and module-version pin resolution.

## Domain terms

- **Version** — `AppVersion` entity (`app_versions`). `status`: `DRAFT` → `PUBLISHED` → `RELEASED`; `versionType`: `VERSION` (named snapshot) or `BRANCH` (git-branch head; `name` is a UUID, display name comes from `WorkspaceBranch`).
- **Release** — `apps.current_version_id` points at the released version. Set by apps module `release()`, guarded by env + slug checks.
- **Environment** — `AppEnvironment` (app-environments module), priority-ordered (development=1 → staging → production). Each version carries `currentEnvironmentId`.
- **Promote** — advance a saved version's `currentEnvironmentId` to the next-higher-priority environment. Multi-environment is EE-licensed (`LICENSE_FIELD.MULTI_ENVIRONMENT`).
- **Module pin** — a ModuleViewer component pins a module version via `moduleReferenceId` (stable UUID per version row, survives git/zip round-trips).

## Edition split

- `server/ee/versions/service.ts` extends CE `VersionService`: implements app-history hooks (initial snapshot on create, settings deltas on update); `getVersion` adds page/query/component-level permission filtering (license-gated) and git-branch editor freeze; `promoteVersion` adds module-promotability check + per-environment access check (returns `hasAccessToPromotedEnvironment`).
- `server/ee/versions/util.service.ts`: deletes git tag on version delete; `setupVersionFromSource` — cross-app clone (no appId ownership check) for building BRANCH versions from git-imported temp apps.
- `server/ee/versions/services/create.service.ts` overrides clone internals (incl. `handleModuleViewerComponent`).
- CE behavior when license lacks MULTI_ENVIRONMENT: version pinned to development env, promote throws.

## Invariants & gotchas

- Initial-version creation reads the parent app type without hydrating an `App` entity. Partial app entities trigger editor-state subscribers without the workspace context they need; keep scalar-only lookups free of those side effects.
- Non-DRAFT versions are immutable in name/description (`service.ts` update: "Cannot edit name or description of a saved version"). Content edits are frozen via `should_freeze_editor` (env priority > 1, status PUBLISHED, or EE git freeze).
- Promote: DRAFT cannot be promoted (save first); request's `currentEnvironmentId` must equal the version's, else 406; next env = lowest priority above current; `promotedFrom` is nulled on promote.
- Delete: released version (matches `apps.current_version_id` or status RELEASED) and the only/branch-head version cannot be deleted; module versions in use by apps block deletion (`checkModuleVersionInUse`). `DataQueryFolder`/`DataQueryFolderMapping` need explicit cleanup (no CASCADE).
- Git branching on ⇒ only one DRAFT of type VERSION per branch — but the single-draft unique index is predicated on `is_synced = TRUE` (`1782100000000-ExemptUnsyncedDraftsFromDefaultBranchUniqueIndex.ts`), so an unsynced app may legitimately hold several default-branch drafts. Publishing a default-branch draft (`handleDefaultBranchPublish`) seeds a fresh DRAFT on that branch and **leaves `branch_id` intact on the published row**.
- **PUBLISHED rows keep their default-branch `branch_id`.** The old `chk_app_versions_branched_implies_draft` CHECK is dropped (`migrations/data/1781741000000-MakeAppVersionBranchIdNotNullAndGitSyncFlags.ts:55-58`; the re-add at `:504` is in `down()`), and `branch_id` is NOT NULL once `CleanupLegacyBranchModel` has run (see the next point). Anything reasoning about a *released* app's branch context depends on this: `consumerBranchId` for a released app is the default branch, not null, which is why workflow ref resolution needs a published-consumer backstop (`workflow-ref.util.ts`).
- **A NULL `branch_id` counts as the default branch** until `CleanupLegacyBranchModel` runs (one upgrade after 3.21.58): 3.21.58 pods write rows without one during the rolling upgrade. Branch-scoped reads go through `src/helpers/branch_scope.helper.ts`; a plain `WHERE branch_id = :branchId` drops those rows.
- Non-workflow app metadata (`appName`/`slug`/`icon`/`isPublic`) lives on `app_versions` rows, not `apps.*`. Workflows keep `appName`/`slug`/`icon`/`isPublic` on `apps.*`, but **`workflow_enabled` is a version column** (`app_versions.workflow_enabled`, the fifth member of the propagate-trigger set) so webhook enablement is branch-scoped and travels through git. For this release `propagate_workflow_enabled()` also copies the default branch's value to `apps.workflow_enabled`, which the previous release reads after a rollback; the version column is NULL until backfilled and readers fall back to the app value.
- Publishing an app version blocks if any ModuleViewer resolves to a draft/orphan/unpinned module (`checkDraftModulesInApp`), or if any workflow query resolves to a DRAFT version (`checkDraftWorkflowsInApp`); EE promote blocks if a pinned module version isn't yet in the target environment. The workflow twin deliberately treats an **unpinned** query as *not* an offender — unpinned means "run whatever is released", which every existing app relies on. Only the module check faults unpinned. When a workflow is blocked only by draft pins (save), unpromoted pins (promote) or unreleased pins (release, `checkWorkflowsReleasedInApp`), the error also carries `code: 'NESTED_WORKFLOW_PINS_BLOCKED'`, `action` and `workflows`, which the editor shows as a dialog.
- `checkTablesPromotableToEnvironment(appId, versionId, targetEnvironmentId, targetEnvironmentName, sourceEnvironmentId, organizationId, manager)` still hard-blocks (throws `BadRequestException`) a table with zero relation in the target environment, unchanged. `versionId` scopes the underlying `findTooljetDbTables` lookup to that one version — without it, a table referenced only by an abandoned draft (never promoted, never revisited) blocked every future promote of the app with no UI showing why. It additionally returns `Promise<{ warnings: TableBehindWarning[] }>` (not `void`) for tables that DO resolve a target relation but are behind on migrations — that half is warn-only, never blocks. Both promote call sites — interactive `server/ee/versions/service.ts` and External API `autoDeployApp` (`server/ee/external-apis/service.ts`) — thread `warnings` through as a `tableWarnings` field on their response. Treat `tableWarnings` as part of the promote response's wire format now. The check runs for front-end apps, modules and workflows alike (each runs its own queries); only the module-embed check stays front-end-only. `findTooljetDbTables` also resolves SQL-mode (`sql_execution`) queries by table name in the app's workspace, after replacing `{{ }}` bindings with a literal; a query whose table name is itself a binding is skipped.
- `co_relation_id` is only unique per-organization (git clones share it) — always scope lookups by org.
- **Copying an app-level (local) data source into a new version needs `organizationId` and a unique name.** The default DSV's `branch_id` is resolved by joining `data_sources.organization_id` (null → 23502), and `(name, branch_id)` is unique per workspace (clash → 23505), so the copy goes through `generateUniqueName`: `name`, `name_2`, `name_2_2` for a copy of a copy. EE overrides `createNewDataSourcesAndQueriesForVersion` with its own copy of this logic — change both.
- **A component's `co_relation_id` is its identity across versions, and the version compare (EE `versions/diff/`) matches by it.** Within a page the base's components match the target's by id, then by name (`componentAliases`), so a rename is one changed component, not a removal plus an addition. It is set when a component is created (`ComponentsService.transformComponentData`), and a version copy gives one to any component that lacks it, on the source row too (`assignMissingComponentCoRelationIds`) — there is no backfill. Queries and pages still match by name/handle. Items inside a list property (table columns) match by their `key`, falling back to `name`/`label`/`id`, so a renamed header or any other edit reads as `edited <column>`, not added plus removed (`describeListChange`, EE `versions/diff/describe.ts`). The target is never aligned, so `contentFingerprint` does not depend on the other version.
- **Orphaned module pins fall back only on feature branches.** `resolveModuleRef` (the `module/by-correlation/:coRel/version` fetch) resolves a UUID/name pin that matches no tier by falling back to the module's own row on the consumer's *non-default* branch — never on the default branch, where an unhonorable pin still returns null (404). This mirrors `resolveAllModuleViewersForVersion` (app-load), so the two agree: without it the parent app renders the ModuleViewer via its orphan-fallback while this endpoint 404s, blanking the embed. Keep the default-branch strictness — an explicit pin there must resolve to a servable row (PUBLISHED / legacy `isSynced:false`), not silently swap to a synced draft (see `module-ref-resolution.spec` "synced draft name-pin still 404s").
- **`__current_branch__` never crosses a branch boundary.** On a feature branch, Tier C returns that branch's BRANCH row or **throws** — it does not fall back to the default branch's draft (`workflow-ref.util.ts`, Phase 10 Step 10.4). A stub counts as absent (`isStub: false` is part of the lookup); the pull and app-open hydrate cascades are what make that state self-healing. The default-branch arm still serves the two callers that *should* reach it: publish/promote checks, which omit `consumerBranchId` deliberately, and consumers already on the default branch — which includes **released apps** (see the PUBLISHED-rows note above). Pinning main's draft explicitly is what `__default_branch_draft__` is for. Covered by `test/modules/versions/unit/resolve-workflow-ref.spec.ts` (full-tier spec; its Tier C block holds the branch-arm throw cases and both default-branch arms).
- **"Unpinned" means opposite things for a ModuleViewer and a workflow query.** The two resolvers are otherwise twins, so this is the trap the split into `module-ref.util.ts` / `workflow-ref.util.ts` makes visible rather than hides. A ModuleViewer with no pin *follows the consumer's branch*; a workflow query with no pin *runs whatever is released*. The module viewer also encodes unpinned as `''` while a workflow query encodes it as absent/null. Never generalise a fix from one file to the other without re-deriving which semantic applies.
- New versions/drafts always start on the lowest-priority (development) environment regardless of source.
- **Review decisions are audited by hand.** Audit entries exist only when a handler calls `RequestContext.setLocals(AUDIT_LOGS_REQUEST_CONTEXT_KEY, …)`; `auditLogsKey` on a feature only names the action. `VersionReviewService` (`server/ee/versions/reviews/`) does it after each `step()` / `open()` commits, with a per-event `REVIEW_AUDIT_KEYS` action type (comments and reviewer changes are not audited). The override's reason is in the entry's metadata, since review activity does not outlive its app. Extra action types a feature writes go in `auditLogsKeys` so the audit log filter lists them.
- **Whether reviews are required is a workspace setting, "Reviewers needed"** (`organizations.review_approvals`, Workspace settings → App review & security, `GET`/`PUT /app-security/review-settings`, admins change it). 0, the default, is off. N > 0 gates Save version (every draft, `assertDraftSavable`), release and promotion to production behind N approvals; a review stores N in `required_approvals` when it opens, so a later change of the setting leaves open reviews as they are. `reviewPolicy(manager, organizationId)` reads it; `gate` reads it with the app row. Under git branching release and promotion stay ungated (the pull request is the gate); Save version is not. Promotion before production (`move`) is never required, but waits on an open review.
- **A review can be opened on a DRAFT, and the draft stays editable.** Approvals are bound to the content fingerprint (`status` is not in it), so saving an approved draft keeps its approval and an edit makes it stale. A stale approval is announced once: `reviewState().resetPending` lists approvers whose approval is newer than the last `approvals_reset` event, the editor's 60s brief poll (`list(..., brief)` reads the live fingerprint) reports `resetPending`, and the editor then calls `POST /apps/:id/reviews/:reviewId/reset-check` (`resetCheck`, row-locked, idempotent), which writes the event and emails the creator and those approvers. An announced reset voids the approvals it announced (`reviewState` moves them to `staleApprovals`), so changing the content back to what was approved does not revive them: the reviewer approves again, or the author asks again. A revert before the reset is announced changes nothing. `rereview_requested` also works for stale approvals. The dashboard bell (`waitingReason`) mirrors the emails: the author is told of an approval (`approved`) and of a reset (`approvals_reset`), an approver of the reset of theirs, each until they act. Git-branch drafts follow the next two bullets.
- **Compare spans git branches.** With git branching on, the compare view asks `GET /apps/:id/versions?includeAllBranchVersions=true`, which returns every non-stub row of the app across branches, the current branch's rows first (`getVersionsOfEveryBranch`); a BRANCH row carries `displayName` (its branch's name, its own `name` is a uuid). The view compares a branch draft with the default branch's draft by default. Compare reads ToolJet's drafts, not git commits, so uncommitted edits show and a branch pulled but not opened yet does not (stubs are not listed).
- **A review of a git branch draft covers committed content only** (`server/ee/versions/reviews/branch-review.ts`). Each push stores the pushed content's fingerprint in `app_versions.committed_fingerprint` and its rows in `committed_content`; the compare view shows a branch draft as that commit (snapshot id `c:<versionId>`, `diff/committed-snapshot.ts`), while `target.fingerprint` stays live; `open` and approving refuse a BRANCH draft whose live fingerprint differs (`UNCOMMITTED_MESSAGE`). The review gate is at the pull request, not at release: `gate` still lets release and promotion through under branching (stored flag plus the multi-branch licence), since the default branch only gets content through pull requests, but `save` (a branch draft saved as a version, which skips the pull request) needs what `release` needs. `GET /workspace-branches/:id/review-status` (`loadBranchReviewStatus`) says whether every committed app of the branch is approved on its committed content (`ready`, informational). The pull request comes first: `open` refuses a review of a branch draft whose branch has no open pull request (`NO_PULL_REQUEST_MESSAGE`), asked from the git side through `BRANCH_PULL_REQUEST_EVENT` (`emitAsync`, answered by `WorkspaceBranchService.openPullRequestOfDraft`; asked before the transaction, since it calls the git provider), and Create pull request is never held back: ToolJet's check on the pull request holds the merge. A pull request merged before that (webhook PR-merged event, or that endpoint seeing the PR merged) writes a `merged_unapproved` event on each unapproved open review, once per PR, plus a `REVIEW_MERGED_WITHOUT_APPROVAL` audit entry; it never blocks, git has merged already. Deleting a branch invalidates the reviews of its drafts (`invalidateReviewsOfBranch`, before the bulk delete). Steps with no ToolJet user (webhooks) are attributed to a workspace admin, else the review's author.
- **A git branch draft's approval is judged on its last commit, and only a new commit or a pull resets it.** `VersionReviewService.reviewedFingerprint` is `committed_fingerprint` for a BRANCH draft (live content otherwise), used by the review list, the editor's poll, `resetCheck` and every step's event fingerprint, so uncommitted edits never make an approval stale. Approve and Request review stay blocked until the draft matches its commit (checked against live content, before the content-changed check). A push from ToolJet (`AppGitService.gitPushApp`) and a pull that writes a feature branch draft (`PlatformGitPullService.hydrateStubApp`, which also records the pulled content as committed) emit `BRANCH_DRAFT_COMMITTED_EVENT`; `WorkspaceBranchService.afterBranchDraftCommitted` runs `resetOnCommit` (an `approvals_reset` event whose body is `commit` or `pull`, `approvals_reset_commit|pull` emails, a `REVIEW_APPROVALS_RESET` audit entry), then re-stamps the PR comment for the head. Saving a branch draft as a version still checks live content, since that is what gets saved. The legacy per-app pull (`orchestrateBranchingPull`) and conflict resolution recreate the draft row, which leaves its reviews pointing at a deleted version.
- **The merge is blocked in git through ToolJet's PR comment (GitHub only).** ToolJet keeps one comment on a branch's open pull request (`server/ee/versions/reviews/branch-review-comment.ts`, `WorkspaceBranchService.syncReviewComment`), found again by its hidden block `<!-- tooljet-review {"state","sha"} -->`. `sha` is the PR's head commit at an approval, a new review or a push from ToolJet (`refreshCommit` on `BRANCH_REVIEW_COMMENT_EVENT`); every other update keeps the commit the comment already names (`readReviewBlock`), so a commit pushed in git after the approval is never stamped approved. A workflow in the customer's repo reads the block from ToolJet's bot and posts the `tooljet/approval` status that a ruleset requires, passing only when the block is `approved` for the PR's head. Known gap: a commit pushed in git between ToolJet's last commit and the approval is stamped, though the reviewer saw ToolJet's committed content. The comment is written only where the workspace needs reviewers and the plan has reviews, after `BRANCH_REVIEW_COMMENT_EVENT` (review steps other than comments, `resetCheck`, app and workspace pushes; `ReviewCommentListener`), on the PR opened/reopened webhook, and on every `review-status` read, which returns its verdict and commit as `reviewComment`. GitLab gets none: it cannot run a pipeline from a comment.
