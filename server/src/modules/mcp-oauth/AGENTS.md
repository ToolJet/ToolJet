# mcp-oauth module

Owns external MCP client registration, browser consent, rotating credentials and constrained ToolJet delegation.
Deployment and protocol configuration lives in `ToolJet/tooljet-mcp`, `docs/oauth.md`.

## Boundaries

- This release is Cloud-only: both `TOOLJET_EDITION=cloud` and `MCP_OAUTH_ENABLED=true` are required. `isMcpOAuthEnabled` is shared by backend settings, login evidence/cleanup, protocol middleware and public config. CE and self-hosted EE keep their normal login/PAT behavior.

- Pending DCR clients form a rolling cache (1,000 entries, one hour); registration prunes synchronously under the cross-replica registration lock. Only approved/legacy clients spend the 10,000 hard cap, checked on first consent. Cleanup and consent take the registration lock before row locks.
- `throttle.guard.ts` trusts only configured proxy CIDRs. Verified token possession/client authentication and signed delegation select per-grant buckets; unverified traffic uses separate bounded address buckets. Normalize IPv6 callers to /64, evict oldest rate windows at capacity, and require a live grant. Never key token limits by an unverified client ID or JWT claim.

- `service.ts` owns browser consent and token issuance; `identity.service.ts` handles per-request credential checks without depending on the browser flow. `parsers.ts` and `policy.ts` hold shared configuration/registration parsing and policy loading. `engine.ts` adapts the OAuth engine to `store.ts`.
- `claims.ts` is shared by credential signing and runtime validation. Viewer credentials use a distinct audience, are app-pinned, and cannot become browser sessions, PATs or full delegations.
- The JWT strategy resolves Git branch context for delegated and viewer identities, including principals cached by the global guard. Preserve browser/PAT precedence: `branch_id`, legacy `x-branch-id`, then the authenticated workspace's default branch. Authenticate and validate workspace/app bindings before resolving the branch.
- `dto.ts` defines the browser API contracts. Map database rows explicitly; preserve existing wire fields when storage changes.
- Scope checks in `scope.interceptor.ts` share the PAT capability ceiling. They never replace the user's current permissions, workspace binding or edition gates.
- Only the configured MCP service may exchange an access token. A mismatched exchange secret returns `401 invalid_client` internally; the MCP boundary reports a service failure (503) without a user login challenge. Never log secrets or credential bodies.

## Revocation and concurrency

- `revocation.ts` is the single awaited application implementation for Cloud credential invalidation. Explicit service/repository write helpers cover user status, workspace status/slug/login restrictions, memberships (including bulk and external APIs), SSO/group sync and instance login settings. Instance bans and administrative termination call the same credential invalidator once in their transaction; password resets and profile password changes retain invalidation. Ordinary logout remains session-only. Do not use unawaited events or ORM subscribers for security changes.
- Platform changes take the shared policy advisory lock BEFORE modifying security rows. Consent locks its client, then takes the exclusive policy lock before inserting a grant and rechecking live policy/session state. Independent administrative updates can proceed concurrently; approvals briefly serialize. PAT mint/exchange take a user-row SHARE lock, while credential invalidation takes the policy lock before a user-row NO KEY UPDATE lock. Keep this order and the consent recheck barrier.
- Recoverable OAuth/PAT write errors are isolated with savepoints and warnings so normal platform operations continue. Never log database error bodies or credentials. Successful invalidation is atomic with the platform action; failed invalidation is best effort. Live checks reject current restrictions, but restoring a restriction can revive a credential whose durable revocation failed. There is no failure-state circuit breaker; cancellation/assertion failures are not swallowed.
- The three unreleased OAuth migrations install tables/indexes without runtime triggers or an existing-credential revocation backfill. The ban-email lookup index is the only added schema object on an existing platform table; migrations do not update existing PATs or ban records. No legacy trigger-cleanup migration is shipped. Direct SQL and data migrations do not invoke application revocation. Live checks detect current restrictions, but a direct SQL change-and-restore before a token check is outside durable revocation coverage. Security-changing maintenance scripts must call the awaited invalidator in their transaction.
- Token rotation locks the grant row. Authenticated replay of a consumed code revokes the grant. A refresh retry can recover the same unused child pair within five seconds for the same client, resource and scopes; other refresh replays revoke the grant, including derived credentials. Client authentication precedes replay detection so a wrong client secret cannot revoke someone else's grant. Cached retry responses are AES-GCM encrypted with an artifact-bound associated value and purpose-specific key; never persist plaintext token pairs.
- `persistRevocationOnFailure` persists a rejected grant after the failed transaction rolls back; revoking only inside a transaction that throws would undo revocation.
- Every active-grant check rechecks the workspace policy. `security-policy.ts` provides the same provider-specific security projection to the write comparator and live fingerprint. Display/unknown metadata and an explicit `authorization_code` default are ignored; client IDs/secrets, discovery URLs, scopes, provider authentication modes, SAML metadata, LDAP trust/bind settings and group mapping remain relevant. When adding an authentication setting, add it to this projection and its tests. Stored encrypted secrets remain in the hash; unchanged plaintext preserves its existing ciphertext. OIDC's legacy fixed verifier is not used by the MCP login path.
- Ordinary browser logout is separate from disconnecting an OAuth grant. Do not imply that deleting a browser session revokes all external clients.

## Storage and tests

- Raw SQL is deliberate for explicit row/advisory locks, atomic `UPDATE ... RETURNING` consumption, and transaction-coordinated revocation. Keep queries parameterized and maintain typed boundary mappings. Do not introduce ORM saves that bypass these transaction requirements.
- Credential lookups use hashes; the bounded refresh retry response is encrypted separately. Do not add raw tokens or client secrets to logs, API connection listings or fixtures.
- Run `npm run test:mcp-oauth` from `server/`. Database flow tests require `MCP_OAUTH_TEST_DATABASE_URL` pointing to a disposable local database named `tooljet_oauth_test_*`; the preparation script resets the disposable database’s public schema and uses the production runner for schema and data migrations and also pins historical migrations’ secondary DB connections to that disposable database. It refuses dotenv files. Never run against a normal development database. CI requires the database URL and runs the complete suite.
- Assert specific OAuth error codes or HTTP exception types, not merely that a promise throws. Use synthetic clients, identities and messages.

- Viewer credentials get a separate short-lived access artifact capped by the live grant, so expiration of the minting access token does not interrupt an ongoing render. Viewer app/audience/scope checks and live policy revocation still apply.
- The reviewed PAT/OAuth route inventories live under `test/modules/personal-access-tokens/` and `ee/test/modules/mcp-oauth/`. New reachable controllers or features require explicit inventory review. Enterprise-only tests belong in `ee/test/`; each edition registers its cases through the shared PostgreSQL fixture without public tests importing private code; the OAuth runner includes both trees.
